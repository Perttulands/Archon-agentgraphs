Agents get full access

Seats are ordinary tmux sessions running as the daemon's user, started without permission prompts: Claude Code with --dangerously-skip-permissions, Codex with --dangerously-bypass-approvals-and-sandbox, and Pi, which asks no permissions, with --approve so it trusts the folder's project files for that launch. Archon adds no sandbox. Safety lives in how you configure the agents and the account they run as.

Before you start

  • tmux, at an absolute path you will give the daemon. The tmux client and server must be the same version: a tmux 3.4 client cannot talk to a 3.6a server.
  • The harness CLIs your slots name, signed in: claude for claude-code, codex for openai-codex, pi for pi. Archon never holds or passes credentials.
  • A state directory, as in the lab quickstart, served by no other daemon.

How the tmux executor finds things

WhatWhere it comes from
The tmux serverMust already be running on --socket, owned by the daemon's user. The daemon does not start one; a run that finds none blocks with tmux_server_start_failed. The socket path must be the real path, not a symlink.
The tmux client--tmux-bin, used for every tmux call. The flag's help calls it a "guarded wrapper": a host may point it at a wrapper script, but the plain tmux binary works.
Harness executablesResolved on the daemon's PATH when a seat launches. A service needs a PATH that includes them.
A seat's environmentTaken from the tmux server, not the daemon. API keys and anything else a harness reads from its environment must be in the server's environment, or in the harness's own config files.
CompletionRead from each harness's native transcripts: --claude-transcripts (Claude's projects directory), --codex-transcripts (Codex's sessions directory) and optionally --pi-transcripts (defaults to $PI_CODING_AGENT_DIR/sessions, else ~/.pi/agent/sessions). The first two are required with --executor tmux, even if you only run Pi.

Run one step with a real agent

  1. Start a tmux server for seats

    Give it a socket of its own and start it from a shell whose environment the seats should inherit, with the harness CLIs on PATH. A detached session keeps the server alive.

    export ARCHON_STATE="${XDG_DATA_HOME:-$HOME/.local/share}/archon/state" export ARCHON_SOCKET="$ARCHON_STATE/tmux/seats.sock" export TMUX_BIN="$(command -v tmux)" mkdir -p "$(dirname "$ARCHON_SOCKET")" env -u TMUX "$TMUX_BIN" -S "$ARCHON_SOCKET" new-session -d -s archon-keep

  2. Add a one-step mission

    This is the smallest mission that validates: an Input card, one solo step and an End node, with every route leading somewhere. Staff the slot with the harness you have signed in; Pi is shown, with the other two as comments.

    schema = 1 id = "msn_hello" slug = "hello" title = "Hello" rev = 1 [[inputCard]] id = "inp_hello" title = "Hello" goal = "Return the supplied input" [[formation]] id = "fmn_work" type = "solo" title = "Work" [formation.brief] goal = "Do what the input asks, briefly." [[formation.input]] id = "port_in" label = "Input" [[formation.output]] id = "port_out" label = "Result" [[formation.slot]] id = "slot_work" label = "Worker" harness = "pi" model = "anthropic/claude-haiku-5-5" effort = "low" # harness = "claude-code", model = "haiku" # harness = "openai-codex", model = "" (the Codex default) controller = true [[end]] id = "end_done" title = "Done" outcome = "done" [[connection]] id = "edge_start" from = "inp_hello:out" to = "fmn_work:port_in" [[connection]] id = "edge_done" from = "fmn_work:port_out" to = "end_done:in" archon --workspace "$ARCHON_STATE" mission validate hello

  3. Start the daemon with the tmux executor

    Every path is absolute. The transcript directories below are the harnesses' defaults; adjust them if you moved yours.

    archond --executor tmux \ --state-dir "$ARCHON_STATE" \ --listen 127.0.0.1:8091 \ --socket "$ARCHON_SOCKET" \ --tmux-bin "$TMUX_BIN" \ --claude-transcripts "$HOME/.claude/projects" \ --codex-transcripts "$HOME/.codex/sessions"

    --executor tmux is the default; it is written out here for clarity. Add --ui-dir for a source build, as in the quickstart.

  4. Start the run and wait

    The mission declares no inputs, so it takes the implicit brief. Without --cwd the daemon creates a private workspace for the run under $ARCHON_STATE/workspaces/.

    export ARCHON_SERVER=http://127.0.0.1:8091 RUN=$(archon --server "$ARCHON_SERVER" mission run hello \ --input brief="Reply with the word hello." --json | jq -r .data.runId) archon --server "$ARCHON_SERVER" run wait "$RUN" --until final archon --server "$ARCHON_SERVER" run attempts "$RUN"

    While it runs, open the cockpit, choose the run and click the Work card: its window is the seat's terminal. You can type to the agent there, even while it works.

What happens in the seat

The daemon creates a tmux session named archon-<run>-slot_work, launches the harness with the slot's model and effort, and pastes a one-line pointer to a brief file under $ARCHON_STATE/briefs once the agent is idle with an empty input line. The brief tells the agent what to do, which ports to fill and how to finish:

```archon-outputs {"port_out":{"text":"hello"}} ``` << status=ok artifact=>>

Completion counts only when the harness's own transcript shows a finished turn carrying this run's sentinel. The seat is then cleaned up (seat_cleanup outcome ended) and the output moves on to the End node.

When it does not start

You seeDo this
standalone seats require an already running tmux server (tmux_server_start_failed)Start the tmux server on the daemon's --socket (step 1), then archon --server "$ARCHON_SERVER" run resume "$RUN" --reason "started tmux". The failed attempt stays in the history.
<harness> is not on PATHRestart the daemon with a PATH that includes the harness CLI.
--<flag> requires an absolute pathThe daemon refuses to start: every path flag, including both transcript flags, must be absolute.
The run blocks with seat_idle_without_sentinelThe agent went quiet twice for five minutes without finishing. Open the seat, see why, then run resume "$RUN" --mode redispatch.
A Pi seat cannot reach its modelPi resolves its own credentials: sign in with Pi, or put the provider key in the tmux server's environment and restart that server.
