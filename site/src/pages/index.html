What you get

A mission you can read

A mission is one TOML file: an Input card that states what a run supplies, steps that do the work, gates that check it, and End nodes where paths finish. The cockpit, the CLI and agents all edit the same file.

Agents in ordinary tmux sessions

Each staffed slot becomes a seat: a real Claude Code, Codex or Pi session in tmux, with full access. You can open its terminal in the cockpit and talk to it while it works.

Gates that send work back

Gates combine a code check, a judge formation and a human verdict. A failed gate routes its reasons back to the work as the next attempt's feedback.

Runs an agent can drive

The managing agent starts a run and pulls with run wait, which returns when the run needs an answer and prints the exact command that gives it. Archon pushes nothing into anyone's session.

How the parts fit

PartWhat it does
archondThe coordinator. Admits and executes runs, creates and cleans up seats in tmux, writes each run's ledger, and serves the HTTP API and the cockpit. One daemon owns one state directory.
archonThe CLI. Authors missions offline with --workspace or through the daemon with --server, and sends every runtime command (start, wait, answer, resume, abort) to the daemon.
The cockpitThe browser UI that archond serves. It has the Missions view, where you draw, staff, run and answer, and the Agents view, a library of roles and saved characters.
The archon skillInstructions that teach a Claude Code, Codex or Pi agent to author and drive missions with the CLI.

Trust model

Archon adds no sandbox, no file confinement and no authentication. Seats start with their harness's permission prompts turned off (--dangerously-skip-permissions for Claude Code, --dangerously-bypass-approvals-and-sandbox for Codex; Pi asks none). Anyone who can reach the daemon can start, answer and stop runs. Run it only on interfaces you trust. Read more.
