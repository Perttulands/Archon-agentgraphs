Two ways to author

In the cockpit

The row under the top bar holds the building blocks: Formation, Gate, End and Limit. Click Formation to add one, or drag any block onto the canvas. Right-click the canvas for the same choices. Drag from an output port to an input to wire.

Click a card to open its window beside it; every field reads in full and edits in place. Each save is one undo step (Ctrl+Z, Ctrl+Shift+Z). Delete or Backspace removes the selection when the canvas has focus.

With the CLI

Every authoring command works offline on the files (--workspace <state-dir>) or through the daemon (--server <url>). Through the daemon, an open cockpit shows each edit live. There is no default: a command with neither flag says so and stops.

archon -h lists the nouns, archon mission -h a noun's commands, and archon mission run -h one command's flags. See the CLI reference.

Build a reviewed step with the CLI

This builds a step that makes a change, a judge gate that reviews it and sends failures back, an End node, a Limit card and a declared output. Take every ID from the JSON a command returns; never guess one. The commands are for bash or zsh and need jq. With no daemon running, use --workspace "$ARCHON_STATE" in place of --server "$ARCHON_SERVER".

export ARCHON_SERVER=http://127.0.0.1:8091 # your daemon M=review archon --server "$ARCHON_SERVER" mission new "$M" --title "Reviewed change" --json archon --server "$ARCHON_SERVER" mission create "$M" --title "Change" --goal "Deliver a reviewed change" --json archon --server "$ARCHON_SERVER" mission input "$M" change --required --description "What to deliver and why" --json # The step that does the work. A new formation has one input, one output and its slots. WORK_JSON=$(archon --server "$ARCHON_SERVER" formation create "$M" solo --title "Build" --json) WORK=$(jq -r .formation.id <<<"$WORK_JSON") WORK_IN=$(jq -r '.formation.inputs[0].id' <<<"$WORK_JSON") WORK_OUT=$(jq -r '.formation.outputs[0].id' <<<"$WORK_JSON") WORK_SLOT=$(jq -r '.formation.slots[0].id' <<<"$WORK_JSON") archon --server "$ARCHON_SERVER" formation assign "$M" "$WORK" --slot "$WORK_SLOT" \ --harness openai-codex --effort medium --role builder --json archon --server "$ARCHON_SERVER" formation set-brief "$M" "$WORK" --goal "Make the change: {change}" --json archon --server "$ARCHON_SERVER" mission wire "$M" "$WORK:$WORK_IN" --json # Input card -> Build # A judge, and a gate it decides. JUDGE_JSON=$(archon --server "$ARCHON_SERVER" formation create "$M" solo --title "Judge" --json) JUDGE=$(jq -r .formation.id <<<"$JUDGE_JSON") archon --server "$ARCHON_SERVER" formation assign "$M" "$JUDGE" --slot "$(jq -r '.formation.slots[0].id' <<<"$JUDGE_JSON")" \ --harness claude-code --model opus --effort xhigh --role judge --json archon --server "$ARCHON_SERVER" formation set-brief "$M" "$JUDGE" --goal "Judge whether the work delivers {change}." --json GATE=$(archon --server "$ARCHON_SERVER" gate create "$M" --kinds formation --title "Review" \ --criterion "The change satisfies the brief" --json | jq -r .gate.id) archon --server "$ARCHON_SERVER" gate judge "$M" "$GATE" --chain "$JUDGE" --json # Route everything: work into the gate, FAIL back, PASS to an End node. archon --server "$ARCHON_SERVER" formation wire "$M" "$WORK:$WORK_OUT" "$GATE:in" --json archon --server "$ARCHON_SERVER" formation wire "$M" "$GATE:fail" "$WORK:$WORK_IN" --json DONE=$(archon --server "$ARCHON_SERVER" end create "$M" --json | jq -r .end.id) archon --server "$ARCHON_SERVER" formation wire "$M" "$GATE:pass" "$DONE:in" --json # Optional: cap the loop, and promise an output. archon --server "$ARCHON_SERVER" limit create "$M" --target "$WORK" --rounds 3 --when-spent best --json archon --server "$ARCHON_SERVER" mission output "$M" result --from "$WORK:$WORK_OUT" --required \ --description "What changed" --json archon --server "$ARCHON_SERVER" mission validate "$M" archon --server "$ARCHON_SERVER" mission arrange "$M" --json > /dev/null

mission validate should print review 0 errors 0 warnings. After building or rewiring a graph, mission arrange lays it out in compact reading rows. Arrange replaces saved positions, so use it on purpose; ordinary edits place new cards without moving others.

The Input card

The Input card is the mission's entry and its contract with whoever runs it. It holds the goal, the inputs a run supplies, the outputs a successful run promises, optional reference files and how human gates reach the operator (the human channel).

archon --server "$ARCHON_SERVER" mission update "$M" --title "Change" --goal "Deliver a reviewed change" archon --server "$ARCHON_SERVER" mission update "$M" --file /abs/path/to/rubric.md # repeat; --file '' clears

Inputs

Declare what a run must supply instead of baking specifics into briefs. A name is a lowercase letter followed by lowercase letters, digits or underscores. The kind is text (the default), file or folder; an input is optional unless required.

archon --server "$ARCHON_SERVER" mission input "$M" change --required --description "What to deliver and why" archon --server "$ARCHON_SERVER" mission input "$M" spec --kind file --description "An existing spec to follow" archon --server "$ARCHON_SERVER" mission input "$M" # list what a run supplies archon --server "$ARCHON_SERVER" mission input "$M" spec --delete

Briefs reference inputs as {name}. Each seat's brief gets the value in its place, or (not supplied) for an optional input left out. {bead} takes the run's --bead unless the mission declares an input named bead. Write {{name}} to show a seat a literal {name}. A reference to an undeclared name is the validation error unknown_input_reference.

A mission that declares no inputs takes one required text input, brief, described by the Input card's input hint (mission update --input-hint).

Outputs

Declare what a successful run promises so an agent can chain the mission without reading its steps. Each output is bound to one step output port of the same kind.

archon --server "$ARCHON_SERVER" mission output "$M" report --kind file --from "$WORK:$WORK_OUT" --required --description "The final report" archon --server "$ARCHON_SERVER" mission output "$M" # list them

When the run ends at a done End, each output is the payload of its bound port that went down the path to that End, never an attempt a gate rejected. A required output the path never delivered fails the run with missing_output. A run that ends at a rejected End promises nothing.

Steps, ports and briefs

A step's brief says what it does (formation set-brief --goal, plus --file for reference files). Keep everything mission-specific in briefs: roles are generic and shared across missions. Name reference files by absolute path; authoring refuses a relative one (relative_file_reference), and a file that does not exist yet saves with a warning.

Output ports carry text (the default), a file or a folder. For a file or folder port the seat returns an absolute path, and Archon keeps a read-only copy of that attempt's version, so a send-back loop that rewrites one project file keeps every version.

archon --server "$ARCHON_SERVER" formation add-output "$M" "$WORK" --label site --kind folder archon --server "$ARCHON_SERVER" formation set-port "$M" "$WORK" "$WORK_OUT" --kind file archon --server "$ARCHON_SERVER" formation inspect "$M" "$WORK"

Edit nodes in place so their wires survive: formation rename, formation set-type, mission update, gate update. An empty value clears a field.

Fan out and join

An output port feeds any number of inputs. Every step whose inputs have arrived starts at once, so the branches of a fan-out work at the same time. Each formation input takes one feed, and a formation starts only when every input port has a delivery. To join, wire each upstream with --join: an occupied input gains a new port and its wire in one edit.

archon --server "$ARCHON_SERVER" formation wire "$M" "$WORK:$WORK_OUT" "$REV1:$REV1_IN" archon --server "$ARCHON_SERVER" formation wire "$M" "$WORK:$WORK_OUT" "$REV2:$REV2_IN" archon --server "$ARCHON_SERVER" formation wire "$M" "$REV1:$REV1_OUT" "$LEAD:$LEAD_IN" --join archon --server "$ARCHON_SERVER" formation wire "$M" "$REV2:$REV2_OUT" "$LEAD:$LEAD_IN" --join

Gate and Tool inputs stay single-feed. In the cockpit, dropping a wire on a fed input makes the same join.

Notes

Notes are the operator's intent, shown as stickies on the canvas. They are threads: append, and change only your own entries. An agent that builds a step should explain it on the step's thread in words the operator reads on the canvas.

archon --server "$ARCHON_SERVER" mission notes "$M" archon --server "$ARCHON_SERVER" mission note "$M" --node "$WORK" --text "Here a builder makes the change; a judge reviews it and sends it back with reasons."

Validate

mission validate lists every finding that would stop a run, naming each node by title and ID, and exits 1 on any error. Run admission performs the same checks and refuses with HTTP 422 RUN_ADMISSION_FAILED, recording no run. Common findings:

FindingMeans
route_leads_nowhereA step output or a gate route is not wired to a step, gate or End node.
unstaffed_slotA slot has no harness and effort.
unknown_input_referenceA brief names {x} but the mission declares no input x.
unbound_mission_outputAn output has no from, or names no step output port.
invalid_limitA Limit card is unwired, doubled on one target, or has a bad value.
unreachable_node (warning)No path from the Input card reaches this node.

Where missions live

.archon/missions/.mission.toml the mission .archon/notes/.notes.toml its note threads .archon/layout/.layout.toml card positions .archon/runs/ run ledgers and frozen snapshots .archon/artifacts//// each attempt's evidence agents/ role cards that add or override roles briefs/ the brief files seats were given workspaces// automatic run workspaces

Any of these may be a symlink, and so may a single mission file, for example one kept in a project repository: Archon reads and writes through the link. A mission whose link lost its target lists as broken and the rest keep working. Mission files are read as strict TOML; a hand edit that repeats a key is refused, never read leniently. Delete

mission delete removes the mission and its layout and keeps run history. formation delete removes a step, its wires and its Limit cards. gate delete removes a gate and its routes; its judge formations remain.
