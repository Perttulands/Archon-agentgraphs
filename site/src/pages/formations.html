Three types

TypeSlotsHow it works
soloExactly oneOne seat does the step and returns its output.
peerTwo or more, no controllerEach seat writes an independent opening; then they converse through a journal until every peer acknowledges one proposed output.
orchestratedOne controller and at least one workerThe controller receives the brief and directs only its own bound workers, then returns the step's output.

These are the only types; anything else is refused with UNSUPPORTED_FORMATION_TYPE. Change a type in place with formation set-type or the type chip on the card. Changing to solo with several staffed slots needs --keep-slot <slot> to say which one stays.

Slots

A slot owns its harness, model and effort, plus an optional role. Staffing always states the slot in full:

Commands on this page are for bash or zsh and need jq. Take step, slot, gate and run IDs from the JSON a command returns (formation list "$M", run status "$RUN" --json); never guess one.

export ARCHON_SERVER=http://127.0.0.1:8091 # your daemon M=review # the mission slug STEP=fmn_... # a step ID from: archon --server "$ARCHON_SERVER" formation list "$M" SLOT=... # a slot ID from: archon --server "$ARCHON_SERVER" formation inspect "$M" "$STEP" archon --server "$ARCHON_SERVER" formation assign "$M" "$STEP" --slot "$SLOT" \ --harness claude-code --model opus --effort xhigh --role reviewer archon --server "$ARCHON_SERVER" formation unassign "$M" "$STEP" --slot "$SLOT" archon --server "$ARCHON_SERVER" formation list "$M"

--harness and --effort are required. A blank or omitted --model means the harness default. Omit --role for a vanilla agent.

Staffing in the cockpit

Every slot reads as a row: its harness mark, its role (or vanilla) over Claude · opus · low. Clicking a slot opens the staffing sentence where the slot is:

Worker 1 is [vanilla] on [Claude Code] · [opus] · [low]

Each bracketed word opens its own list. The first word also takes typed words in any order (cri ast, sonnet high), digits 1 to 6 set the effort, and N on the canvas jumps to the next empty slot. Dragging a role from the rail onto a slot staffs it; dragging one staffed slot onto another moves or swaps the staffing.

Roles and characters

Roles

A role is role text only: a name, kind, summary, capabilities, status and notes. It never carries a harness, model or effort, and the API refuses a role card that tries. The seven built-in roles are scout, planner, builder, judge, orchestrator, debugger and reviewer; a card in the agents directory (default <state-dir>/agents) adds a role or overrides a built-in one.

agent retire takes a role out of staffing and names the slots that use it; those slots stop validation with retired_persona until restaffed or restored. agent delete works only while no slot names the role.

Characters

A character is a saved staffing: a name, an optional picture, and a role, harness, model and effort. It is a stamp: stamping copies the four values onto the slot and keeps no link. Make and edit them in the Agents view; on the CLI, agent characters lists them and formation assign --character <id> stamps one, with any of --role, --harness, --model or --effort given beside it winning.

The Agents view is the library of roles and characters. Picking a role shows every slot, in every mission, that uses it; a use opens its mission on Missions, where slots are staffed.

Peer formations

A peer step collects one independent opening from every seat before sharing them, then the same seats converse concurrently through an append-only journal for that run, step and attempt. There is no fixed turn order and no facilitator. Seats use the local archon --workspace <state> peer commands to read, post, wait, propose and ack.

Any peer can propose the full output; every peer, its author included, must acknowledge it, and a contested proposal needs revision and fresh acknowledgements. The agreed result must still satisfy the step's declared output ports. Without a Limit card the conversation runs until it agrees; on a peer step a card's rounds counts journal messages. See ADR-0020.

Orchestrated formations

The controller's brief names its bound workers, and it may direct only those. Workers' briefs name the same attempt directory. Archon dispatches the controller; the controller pastes work to its workers, and their token use counts from the pointers it pastes. Agents other than an orchestrated controller must not type into seats or manage their sessions.

Running one step

formation run <mission> <step> (▶ on a card) runs that step on its own, with the mission's inputs and the same run flags. Its step receives the inputs as a first step does, and its routes are ignored.

A role's own session

Outside missions, archon agent spawn <id> --harness <h> --effort <e> [--model <m>] starts a tmux session named after the role, and agent attach joins it. It refuses a role that is already running. These two commands work offline only.
