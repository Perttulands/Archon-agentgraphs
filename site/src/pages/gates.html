Kinds

A gate has a criterion and any non-empty combination of three kinds. They run in this order and stop at the first failure:

KindDecides byConfigure
codeA string check on the output: output_contains@1 or output_absent@1. It runs no shell commands.--kinds code --check output_contains --check-version 1 --check-value <text>
formationA judge chain of agent formations. The last judge's verdict decides.--kinds formation, then gate judge --chain <formation>
humanAn explicit operator verdict. There is no default verdict and no timeout.--kinds human, the default for a new gate

Real checks such as tests, lint or code review belong in a judge formation, whose agents can run anything. A gate's ports are in, pass, fail and judge; every pass and fail must lead to a step, another gate or an End node.

Commands on this page are for bash or zsh and need jq. Take step, slot, gate and run IDs from the JSON a command returns (formation list "$M", run status "$RUN" --json); never guess one.

export ARCHON_SERVER=http://127.0.0.1:8091 # your daemon M=review # the mission slug WORK=fmn_... WORK_IN=port_... WORK_OUT=port_... # the step under review and its ports JUDGE=fmn_... # the judging step NEXT=fmn_... NEXT_IN=port_... # where a pass goes SIGNOFF=gate_... # a gate whose verdict ends the mission RUN=run_... # a run waiting at a gate GATE=$(archon --server "$ARCHON_SERVER" gate create "$M" --kinds formation,human --title "Review" \ --criterion "The change satisfies the brief" --json | jq -r .gate.id) archon --server "$ARCHON_SERVER" gate judge "$M" "$GATE" --chain "$JUDGE" archon --server "$ARCHON_SERVER" gate update "$M" "$GATE" --kinds human # dropping a kind drops its configuration archon --server "$ARCHON_SERVER" gate judge "$M" "$GATE" --detach

Judge chains and the verdict contract

A judge chain is the formations wired from the gate's judge port and back to it, step to step. Each judge reads the work and the judges before it; a chain that leaves the steps, loops or never returns makes the gate incomplete. The runtime appends the verdict contract to every judge seat's prompt. A judge ends with exactly one block, separate from its ordinary output block:

```archon-verdict {"verdict":"pass","reason":"Required checks passed","evidence":["check report reference"]} ```

verdict is pass or fail, reason a string, evidence an array of strings, and nothing else. A malformed block gets one correction turn in the same live seat. If the correction is still wrong, the run blocks resumably with invalid_judge_result: run resume asks the final judge again in a new attempt, keeping earlier judges' reviews, and run resume --take-fail settles the gate as a fail instead. The gate's window offers both as Ask the judge again and Take it as a fail.

Pushback: sending work back

Wire a gate's fail back to the step whose work it judged, and a failure becomes the next attempt. The fail route delivers typed feedback: the gate, its attempt, the verdict, the reason, the evidence and the original input. The next brief shows it as a gate-feedback section.

archon --server "$ARCHON_SERVER" formation wire "$M" "$WORK:$WORK_OUT" "$GATE:in" archon --server "$ARCHON_SERVER" formation wire "$M" "$GATE:fail" "$WORK:$WORK_IN" # the pushback edge archon --server "$ARCHON_SERVER" formation wire "$M" "$GATE:pass" "$NEXT:$NEXT_IN"

Nothing caps the loop except a Limit card: without one, work goes back until the gate passes or someone stops the run. There is no automatic loop detection.

Human gates

A human gate holds up only the work behind it. Other branches keep running, several human gates can wait at once, and each is answered on its own. While a gate waits, the run's status is waiting_human, the cockpit marks the gate with a gold ring and waiting for you, and the navigator counts it under Needs you.

Answering in the cockpit

The gate's answer panel shows the routed input, where each verdict leads, a response box, and Approve and Send back. It says whether a verdict ends its path and whether the run would then succeed or fail.

Answering from the CLI

A verdict names the exact pending request by its sequence, so a stale or duplicate answer is refused with 409. run wait prints both commands with the right --requested-seq when a gate asks.

archon --server "$ARCHON_SERVER" run gates "$RUN" # pending gates and their request sequences archon --server "$ARCHON_SERVER" gate request "$RUN" "$GATE" # the question, routed input and routes archon --server "$ARCHON_SERVER" gate approve "$RUN" "$GATE" --requested-seq 42 --response "Ship it; keep the old flag one release." archon --server "$ARCHON_SERVER" gate reject "$RUN" "$GATE" --requested-seq 42 --response-file /abs/review.md

On approve, a nonempty response travels with the approved input to the next step, rendered as a human-response section. On reject, the response becomes the feedback reason. Responses are kept verbatim, whitespace included. A verdict is recorded and routed at once, even while other steps work.

Answering through the asking agents

By default a human gate's ask reaches the operator through the cockpit, run wait and, if configured, the notify command (humanChannel = notify). With mission update --human-channel session, an ask goes instead to the seats whose work the gate judges: the formation behind the gate keeps its seats on call when it finishes, and each gets a brief with the exact approve and reject commands for its own slot.

The operator then talks to that agent, in its terminal or through the cockpit's Talk, and the agent records only a complete, unambiguous verdict with the operator's exact words (--relayed-by <slot>). If a seat cannot receive the ask, it falls back to the notify command once. Read ADR-0019 and the skill's human-gates reference before using it.

End nodes

An End node ends a path on purpose with outcome done or rejected. Its one port, in, takes any number of routes.

DONE=$(archon --server "$ARCHON_SERVER" end create "$M" --json | jq -r .end.id) REJECTED=$(archon --server "$ARCHON_SERVER" end create "$M" --outcome rejected --json | jq -r .end.id) archon --server "$ARCHON_SERVER" formation wire "$M" "$SIGNOFF:pass" "$DONE:in" archon --server "$ARCHON_SERVER" formation wire "$M" "$SIGNOFF:fail" "$REJECTED:in"

A route that leads nowhere is the validation error route_leads_nowhere (Brief sign-off's pass route leads nowhere: wire it to a step or an End node); drafts with one still save, but no run starts.

How a run finishes

A run finishes when every path has ended and nothing else can still run: every formation has produced output since its last delivery, every gate has evaluated its last input, and no human request is open. Then:

  • It succeeds if every path ended at done Ends and no work came through a pick.
  • It fails with path_rejected if any path ended at a rejected End, carrying the routing verdict's reason. Other branches still run to their own ends first.
  • It ends picked if its work reached a done End through a best-attempt pick: failed work carried on, never a pass. See Best of N.

A join that can never receive its missing input is starved, not pending: once nothing else can run, the run fails if a rejection explains it, or blocks with reachable_node_starved.

Steps that work at once

A run starts every step whose inputs have arrived, beside whatever else works: the branches of a fan-out, steps on other paths and the judge chains of gates. A step reads its ports when it starts; work that arrives while it runs waits and starts the next run of it. A gate evaluates one input at a time, oldest first. Where one step must follow another, wire it so. Full rules: CONTRACT.md, Steps that work at once.
