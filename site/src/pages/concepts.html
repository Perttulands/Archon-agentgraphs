The mission

Mission

The reusable unit: one graph in one file, <slug>.mission.toml, with a stable ID, a slug and a revision. A mission works like a skill: it carries everything a run needs, so an agent can start it, send it off inside other work or chain it after another mission. Never call it a board; that was the old name.

Input card (inputCard)

The mission's entry node. It holds the mission's goal, the inputs a run supplies, the outputs a successful run promises, and an out port wired to the first step. A mission has exactly one.

Input

A named value each run supplies: text, file or folder, required or optional. Step briefs reference it as {name}. A mission that declares none takes one required text input called brief.

Output

A named result a successful run promises, bound to one step's output port with from = "<step-id>:<port-id>". Drivers chain missions by passing an output to the next mission's input.

Note

A thread on the mission or on one node, shown as a sticky on the canvas. Notes hold the operator's intent and the conversation about it. They are not instructions to seats: the managing agent turns them into briefs, staffing and wiring.

Steps and the agents in them

Formation, or step

A unit of work on the canvas: the team of agents that does it. In sentences for the operator "step" means the same thing. There are three types and no others:

  • solo: one seat.
  • peer: two or more seats that open independently, then converse until every peer acknowledges one proposed result.
  • orchestrated: one controller that directs its bound workers.
Slot

A position in a formation. The slot owns what its seat runs: a harness (claude-code, openai-codex or pi), a model (blank means the harness default) and an effort. The cockpit writes a slot as a sentence: Worker 1 is vanilla on Claude Code · opus · low.

Role (persona card)

Optional, generic role text on a slot, such as reviewer. A role carries no harness, model or effort. Every Archon has seven built-in roles: scout, planner, builder, judge, orchestrator, debugger and reviewer. A slot without a role is a vanilla agent.

Character

A saved staffing: a name, a role, a harness, a model and an effort. Stamping a slot with a character copies those values and keeps no link.

Seat

A slot's running agent session: an ordinary tmux session named archon-<run>-<slot>. The runtime creates it, briefs it and cleans it up. You may type into it at any time.

Brief

What a formation's seats are told: the step's goal and any reference files. The runtime wraps it with the run's inputs, routed work, gate feedback and the output contract.

Checking and ending

Gate

A criterion checked between steps by one or more kinds, run in this order and stopping at the first failure: code (a string check on the output), formation (a judge chain of agents) and human (the operator's verdict). A gate's ports are in, pass, fail and judge. Verdicts read PASS and FAIL.

Judge chain

The formations wired from a gate's judge port and back to it. Each judge reads the work (and the judges before it); the last one's verdict decides.

Pushback edge

A gate's fail route wired back to earlier work. It delivers the verdict as feedback and starts the next attempt. Only a Limit card caps how many times it loops.

End node (end)

Ends a path on purpose, with outcome done or rejected. Every step output and every gate route must lead to a step, a gate or an End node.

Limit card (limit)

Caps the rounds, time or tokens of one step, or of the whole mission when it covers the Input card. A run has no limits without one, and nothing adds one by default.

Question and answer

What a human gate asks the operator, and the operator's verdict there: Approve or Send back, with a response that travels on with the work.

Runs

Run

One admitted start of a mission, or of a single step on its own. A run freezes the mission, its staffing and its roles when it starts, so later edits change later runs only. The cockpit names a run by its number in its mission: Run 3.

Attempt

One execution of a step. A send-back, a resume that redispatches or a grant starts the next attempt. Each attempt has its own artifact directory.

Driver

The recorded actor that started a run (startedBy), such as agent:archon or human:ui. Shown verbatim.

The operator and the agent

The operator is the person (human:ui in data when acting through the cockpit). The agent is the managing agent the operator works with through the CLI. The managing agent is never a seat.

Ledger and projection

Each run's history is an append-only file of numbered events. Everything you see, in the CLI, the API and the cockpit, is a sanitized projection of that ledger.

How a run moves

  1. Admission. The daemon validates the mission and the supplied inputs, freezes definitions and staffing, records run_started and answers HTTP 202 with the run ID. Any problem rejects the start with every finding listed, and no run is recorded.

  2. Dispatch. Every step whose inputs have all arrived starts at once. Its seats get a one-line pointer to a brief file and work in the run's directory.

  3. Output. A seat finishes with one archon-outputs block naming each declared port, then the run's completion sentinel. The output moves along every wire from that port.

  4. Gates. A gate evaluates one input at a time: code check, judge chain, then the human, and routes PASS or FAIL.

  5. Finish. When every path has ended and nothing else can run, the run succeeds; or it fails because a path reached a rejected End; or it ends picked when its work came through a best-attempt pick.
