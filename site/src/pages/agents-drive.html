Install the skill

The archon skill ships in every archive at share/archon/skills/archon, and in a checkout at skills/archon. Link it where your harnesses discover user-level skills: ~/.claude/skills for Claude Code, ~/.agents/skills for Codex and Pi. The loop below skips a directory that already provides an archon skill and never replaces an existing path.

export ARCHON_SHARE="$HOME/.local/lib/archon/current/share/archon" # or: "$PWD" in a checkout for dir in "$HOME/.claude/skills" "$HOME/.agents/skills"; do mkdir -p "$dir" if [ -e "$dir/archon/SKILL.md" ]; then echo "$dir/archon already provides the archon skill; left unchanged" else ln -sn "$ARCHON_SHARE/skills/archon" "$dir/archon" fi done

The links follow current, so an upgrade updates the skill with the binaries.

Tell the agent where Archon is

The skill reads two values from the environment or your runbook. Give the agent's session both:

export ARCHON_SERVER=http://127.0.0.1:8091 # literal IP, no trailing slash export ARCHON_STATE="$HOME/.local/share/archon/state" export ARCHON_DRIVER="agent:my-session" # optional: recorded as the run's driver

What a good loop looks like

  1. Clarify. The agent reads the mission, its notes and the role roster, and asks you for any missing input or authority, as one question with options and a recommendation.

  2. Prepare. It reuses a mission or builds one through --server, so you watch each edit land in the cockpit, and explains each step on its note thread.

  3. Run on your go. It starts the run only on an explicit go, with the owning Bead and its own session as the actor.

  4. Pull. It leaves run wait running in the background and reacts when it returns. Archon pushes nothing into its session.

  5. Ask and answer. At a gate it brings you the question, the input and where each verdict leads, and records your verdict with your exact words.

  6. Report. It gives the rundown from run attempts and the artifacts: what ran, what passed or failed, what it produced and where the evidence is.

Missions meant to run unattended

  • Give each Limit card --when-spent fail, so exhaustion ends the run instead of waiting for a grant.
  • Leave an admitted run as it is. A grant or a mission edit needs the operator's authority; improvements land between runs.
  • Never pass a picked run's outputs on as if it had succeeded.

What agents must not do

Seats belong to the runtime. A managing agent never types into seats or manages their tmux sessions; only an orchestrated controller directs its own bound workers. The operator, on the other hand, may type into any seat at any time, and the seat treats that as an instruction.

The skill itself is the reference for agents. Read SKILL.md and its references on recovery, human gates, seat output and lab and examples.
